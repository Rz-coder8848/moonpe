# moonpe 项目申报书

**项目名称**：moonpe —— 纯 MoonBit 实现的 Windows PE/COFF 映像读取库
**仓库**：https://github.com/Rz-coder8848/moonpe
**已发布**：`Rz-coder8848/moonpe` 0.5.0（mooncakes.io）
**方向**：二进制基础设施 / 可执行文件格式解析
**许可证**：Apache-2.0

## 一、项目简介

moonpe 读取 Windows 的 `.exe`、`.dll`、`.sys`：DOS/NT 头、COFF 头、PE32/PE32+ 可选头、
16 个数据目录、节表、导入表、**延迟导入表**、导出表、调试目录（PDB）、基址重定位、
资源树与 VERSIONINFO、TLS 回调、CLR/.NET 头、应用清单，并内置一份把结果转成判断的体检报告。全程边界检查，畸形输入给出具体字节偏移而不是崩溃。

## 二、与既有库的关系：不是重复

生态里已有 `xmyd0915/moonar` 0.6.1。它的定位是 **ar 归档与 COFF 对象**：`.a`、GNU thin、
`.lib` 静态库/导入库、`.obj`。moonpe 处理的是 **PE 映像**——已经链接完成、由 Windows 加载器
装载的文件。两者共享的只有 PE/COFF 格式规定的 20 字节文件头与 40 字节节头；PE 映像独有的
DOS 桩、可选头、数据目录、导入导出表、RVA 映射，moonar 没有；归档容器，moonpe 没有。

同一输入的实际输出：

| 输入 | moonar | moonpe |
| --- | --- | --- |
| `System32\kernel32.dll` | `AR001 at byte 0: expected ar archive magic` | PE64 / AMD64 / 8 节 / 104 导入库 / **3 延迟导入库** / 1697 导出 / PDB `kernel32.pdb` / 版本 `10.0.26100.9444` |
| `SysWOW64\kernel32.dll` | 同上（不是归档） | **PE32** / i386 / 102 导入库 / 3 延迟导入库 / 1669 导出 |
| `demo.a`（llvm-ar 打包 `bcheck.o`） | `0  118560  "bcheck.o"` | `bad signature at 0x0: expected the 'MZ' DOS signature` |

**使用者据此能做什么**：拿到一个待发布包里的 `kernel32.dll`，moonpe 能回答"是不是 64 位、
依赖哪些库（含延迟加载）、PDB 在哪、版本是多少、是否需要重定位"；moonar 打不开这个文件，
这些问题一个都答不了。反过来要查 `.lib` 的成员，moonpe 明确拒绝，此时该用 moonar。

**复用关系**：moonpe 不依赖 moonar，不复制其代码；需要读 `.lib` 时应当调用 moonar，
而不是在 moonpe 里重写归档解析。

## 三、PE32 / PE32+ 规范覆盖范围

| 区域 | 覆盖情况 |
| --- | --- |
| DOS 头 / `e_lfanew` / `PE\0\0` | 读取并校验 |
| COFF 头 | 全字段 |
| 可选头 PE32 (`0x10B`) | 全字段（32 位 image base、4 字节栈堆、4 字节 thunk） |
| 可选头 PE32+ (`0x20B`) | 全字段（64 位 image base、8 字节栈堆、8 字节 thunk） |
| 数据目录 | 16 槽全部命名，给出地址、大小、文件映射状态 |
| 节表 / RVA 映射 | 读取，拒绝节内零填充尾部 |
| 导入 / 延迟导入 / 导出 / IAT | 全部可读，名字与序号两种形式 |
| 调试 / 重定位 / 资源 / VERSIONINFO | 全部可读 |
| TLS 回调 / CLR 运行时版本 / 应用清单 UAC 级别 | 全部可读 |
| Exception / Security / Architecture / GlobalPtr / TLS / LoadConfig / BoundImport / CLR / Reserved | 只报地址范围（明确边界） |

## 四、延迟导入：为什么不能排除

发布前依赖检查如果只看槽位 1，会漏掉一整类真实依赖。实测 `shell32.dll`：静态导入 79 个，
**延迟加载 138 个**——漏掉的是 64%。所以本版把延迟导入作为必做项：

- 描述符 32 字节，`Attributes` 的 bit 0 决定后续字段是 RVA 还是虚拟地址；
- thunk 宽度随 PE32/PE32+ 变化（4/8 字节），序号标志在 bit 31/63；
- 终止条件是 8 个字段全零。

两种描述符形式都有实现与对照测试。

## 五、完整格式支持的验收终点

v1.0 的口径是下面七条全部满足：全部可选头字段可读且有跨位宽测试；16 个数据目录全部命名与
映射；导入/延迟导入/导出/IAT 可读；节表/重定位/调试/资源/VERSIONINFO 可读；任意截断只报错
不崩溃；至少三个真实系统二进制（含 PE32 与 PE32+）验证；README 明确记录边界。

**七条已全部达成**（0.5.0）：29 个测试在 wasm 与 wasm-gc 上全过；真实样本覆盖
`System32\kernel32.dll`（PE64）、`SysWOW64\kernel32.dll`（PE32）、`System32\shell32.dll`、
`System32\notepad.exe`。

## 六、使用场景

1. **发布前依赖检查**：列出 DLL 的静态与延迟加载依赖，避免漏打包。
2. **安全初筛**：看导入 API、节权限（是否可写可执行）、重定位规模与版本信息是否异常。
3. **插件校验**：加载前确认位数、子系统、是否需要管理员权限（清单里的 requestedExecutionLevel）、是否有 PDB 可用于崩溃定位。

## 七、实现路径与技术理解

常见做法有包一层 C 库、只做粗略解析、或按规范从零写。前两种会把平台依赖和语义错误带进来，
我选了第三种，并坚持库本身零依赖（只有 CLI 用官方 `moonbitlang/x` 读文件）。

三个容易做错的点：节表的 `VirtualSize` 与 `RawSize` 之间的空洞在文件里不存在，映射时必须拒绝；
真实 DLL 大量使用序号导入导出；32 位字段在 32/64 位平台表现不同，统一用 `Int64` 读再查范围。

## 八、风险与应对

真实系统文件不能进仓库 → 用手写字节构造 PE32/PE32+ 样本，真实文件只在本地验证，结果写进 README。
格式边角多 → 用"未深入解析"清单划清边界，不让核心路径半途而废。
工具链差异 → 库保持纯 MoonBit、只依赖 core，把平台相关部分隔离在 CLI。
