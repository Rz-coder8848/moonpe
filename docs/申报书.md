# moonpe 项目申报书

**项目名称**：moonpe —— 纯 MoonBit 实现的 Windows PE/COFF 文件读取库
**仓库**：https://github.com/Rz-coder8848/moonpe
**方向**：二进制基础设施 / 可执行文件格式解析
**性质**：原创实现（按公开的 PE 格式规范编写，非移植）
**许可证**：Apache-2.0

## 一、项目简介

moonpe 用 MoonBit 读取 Windows 的 `.exe`、`.dll`、`.sys` 文件：DOS 头、NT 头、COFF 头、可选头（PE32 与 PE32+）、节表、导入表、导出表。解析过程全程做边界检查，出错时给出具体字节偏移，不会崩溃。

## 二、痛点与生态定位

MoonBit 已经能读 Linux 的 ELF 文件（`moonbit-community/elf`），但读不了 Windows 的 PE。我按 10 月 20 日更新的 mooncakes 索引查了一遍（共 3153 个包），`coff`、`portable-executable`、`pe-parser`、`dos-header`、`import-table` 这些关键词命中数都是 0，`moonpe` 这个名字也没被占用。

这个缺口挺实在：Windows 上所有程序都是 PE 格式，做依赖检查、插件校验、样本初筛的人都得用这套东西，但 MoonBit 里没有。

## 三、使用场景

1. **发布前检查**：构建出来的 DLL 到底依赖了哪些系统库，有没有不小心引入不该有的依赖。用 `moonpe imports` 一条命令就能列出来。
2. **安全初筛**：看导入表里有没有可疑的 API，看节权限里有没有又"可写"又"可执行"的段。
3. **插件校验**：加载插件前先确认它是 32 位还是 64 位、是 DLL 还是 EXE、子系统的类型对不对，不匹配就拒绝加载。

## 四、核心功能与边界

**已实现**：DOS 头与 `e_lfanew`、NT 签名、COFF 头、PE32/PE32+ 可选头、数据目录、节表（名称、大小、地址、权限）、RVA 到文件偏移的映射、导入表（按名字和按序号都支持）、导出表（含只能按序号访问的符号）、命令行工具 `moonpe info/sections/imports/exports/all`。

**不做**：执行文件、反汇编、数字签名验证、.NET 元数据、资源目录、延迟导入、TLS 回调、重定位。这些都在 README 里写清楚了。

## 五、实现路径与技术理解

常见的做法有三种：包一层现成的 C 库、只做 HTTP 式的粗略解析、或者按规范从零写。前两种会把平台依赖和语义错误带进来，我选了第三种。

有三处细节是这类库最容易做错的：

第一，节表的 `VirtualSize` 和 `RawSize` 不一样，中间那一段在内存里存在但文件里没有。映射 RVA 时如果把这段算进去，读到的是文件里下一节的字节。我的做法是遇到这段直接返回"没有"。

第二，真实 DLL 的导入导出会用序号，不只是名字。只认名字的解析器会把这些条目悄悄丢掉，表面上还成功。两个方向我都保留了序号。

第三，32 位字段在 32 位和 64 位平台上表现不同。统一用 `Int64` 读、再检查范围，超过 2GB 就报错，不让它在不同平台上绕回成不同的值。

## 六、风险与应对

**样本不好带进仓库。** 系统 DLL 有版权，不能放。所以我用手写的字节构造了完整的 PE32 和 PE32+ 镜像，覆盖导入导出和各种畸形输入；真实文件只在本地验证。

**格式边角多。** 资源、延迟导入、TLS 这些暂时不做，写进"不做"里，不让核心路径半途而废。

**工具链差异。** 开发中遇到过旧版编译器不认 `Int32`、原生后端缺 MSVC、格式化结果随版本变化。应对是把解析库保持纯 MoonBit、只依赖 core，文件读取单独放在 CLI 里用官方扩展库 `moonbitlang/x`。

## 七、移植或参考说明

不是移植，是自己写的。库本身没有第三方依赖，也没用 FFI；只有 CLI 用 `moonbitlang/x` 读文件。

写的时候对照了微软官方的 PE 格式文档，另外看了一些成熟实现（goblin 的 pe 模块、Python 的 pefile）的行为来验证字段含义，但没有复制代码，也没有做代码翻译。许可证用 Apache-2.0。

## 八、当前进度

解析库已经能用：头部、节表、导入、导出全部跑通，**13 个测试在 wasm-gc 上全过**，CI 覆盖检查和测试并且已经跑绿。

真实文件验证用的是系统自带的 `kernel32.dll`——PE64、8 个节、104 个导入库、1697 个导出符号，结果和系统工具一致。为了确认畸形输入不会让程序崩溃，还有一个"把合法文件截断成每一种长度都必须正常报错"的暴力测试。
